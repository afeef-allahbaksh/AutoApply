# CLAUDE.md — AutoApply

## Project
Fully automated job application pipeline. Seven stages in sequence:
Profile → Discover Companies → Find Open Roles → Score Fit → Select Projects → Optimize Resume → Apply → Log

Python backend, Playwright for browser automation, Claude API (via shared singleton client with retry) for resume optimization, project selection, and custom question answering. The FastAPI dashboard is the user surface — every workflow runs from the UI. `main.py` is a thin launcher: it parses `--profile` / `--port` / `--host` / `--no-browser`, sets `AUTOAPPLY_PROFILE`, optionally opens the dashboard in a browser, and runs uvicorn. There are no CLI subcommands.

## Architecture notes
- **Tests** — 14 suites / 93 hermetic tests live in `tests/` (pytest-discoverable via `pyproject.toml`). Every test that touches disk uses a `_test_*` profile name so it can't collide with real user data; `shutil.rmtree` on teardown. Claude API, SMTP, IMAP, and Playwright are all `unittest.mock.patch`'d. `pytest` from the repo root runs everything in ~30s; each file can also be invoked directly (`python3 tests/test_X.py`) via a trailing `if __name__ == "__main__":` runner block, useful for ad-hoc debugging
- **Path constants** — `src/paths.py` is the single source of truth for repo-relative paths (`CONFIG_DIR`, `PROFILES_DIR`). Every module that needs `config/` or `profiles/` imports from there. Never recompute with `Path(__file__).parent.parent` outside `src/paths.py` itself — Phase 34's package reorg silently broke two callsites that did, and the bug surfaced only when a user uploaded a resume (Phase 39 testing). `profile_loader.py` and `schemas.py` re-export `PROFILES_DIR` / `SCHEMA_DIR` aliases for back-compat with existing imports
- **Data layer** — All top-level profile-file writes (`profile.json`, `responses.json`, `applications.json`, `companies.json`, `jobs.json`, `resume.json`, `outreach.json`) go through `src/profile_loader.py:_atomic_write_json(path, data, validator=None)` — validates against the file's jsonschema (where one exists), writes to a `.tmp` sibling, then `os.replace`s into place. A mid-write crash leaves the previous file intact. `Profile` exposes instance methods (`save_applications`, `save_responses`, `save_resume`, etc.) for "I already have a Profile loaded" cases, plus `Profile.create(name, data)` for first-time profile creation (setup wizard). Module-level shims (`_save_applications` in applicant.py, `_save_companies` in discovery.py, `save_outreach` in outreach/store.py, `_write_profile` / `_write_responses` in settings.py route) call `_atomic_write_json` directly so they work in test fixtures and partial-setup contexts where profile.json may not exist yet. Lock acquisition stays at the route layer via `src.ui.state.profile_lock` — separate concerns from atomic writes (locks serialize cross-thread RMW, atomic writes give filesystem crash safety; current locks are non-recursive `threading.Lock`, so pushing locks into the data layer would risk deadlock for routes that pre-acquire)
- **Shared API client** — All Claude API calls go through `src/api.py` (`create_message()`) which provides a singleton `anthropic.Anthropic()` client with exponential backoff retry (3 attempts)
- **Parallel I/O** — Company discovery and job fetching use `ThreadPoolExecutor(max_workers=5)` for concurrent HTTP requests
- **Project pool** — Resume can have a `project_pool` array with all available projects. The optimizer picks the best N (matching current project count) per job to maintain one-page format
- **ATS form handling** — Greenhouse uses React Select comboboxes (click→type→pick option pattern) for degree, school, and some custom questions. Date fields use `input[type="number"]` with direct ID targeting (`#start-year--{i}`)
- **ATS package layout** — `src/ats/greenhouse/` is a subpackage split by concern: `fields.py` (CSS selector constants), `selectors.py` (fill/upload/fuzzy-match helpers), `dates.py`, `location.py`, `education.py`, `demographics.py` (EEO + "decline to self-identify" defaults), `custom_questions.py` (Claude-backed Q&A), `application.py` (orchestrator `fill_greenhouse_application`). `src/ats/lever.py` is single-file. `src/ats/ashby/` mirrors the greenhouse layout (fields, selectors, custom_questions, application) — Ashby's form HTML is more standardized so it doesn't need education/demographics/dates submodules yet. `src/ats/applicant_context.py` carries `build_applicant_context` — used by all three ATSes. External callers import from `src.ats.greenhouse` / `src.ats.lever` / `src.ats.ashby` via the `__init__.py` re-exports
- **Job discovery package** — `src/jobs/` is a package: `clients/greenhouse.py` + `clients/lever.py` + `clients/ashby.py` (per-ATS HTTP), `snippet.py` (HTML strip + requirements-section extraction), `filter.py` (pre-LLM keyword + location filtering + dedup), `classify.py` (LLM-driven country / level / fit-score filtering), `discover.py` (8-stage pipeline orchestrator with `on_progress` + `cancel_check` callbacks). External callers import `discover_jobs` from `src.jobs`
- **Apply route package** — `src/ui/routes/apply/` splits single + batch: `shared.py` (`_apply_status_path`, `_apply_task_key`, `_partition_selected`, `_append_completed`, `_load_jobs`), `single.py` (`_apply_worker` + 6 single-job routes), `batch.py` (`_batch_apply_worker` + 6 batch routes). The package `__init__.py` combines both routers and re-exports the helper names tests import directly. Tests must patch `get_browser_context` at the *submodule* level (`src.ui.routes.apply.single.get_browser_context` / `.batch.get_browser_context`) since each worker has its own import
- **Resume naming** — Tailored resumes saved as `{name}_{company}.pdf` (e.g., `john_doe_anthropic.pdf`)
- **ATS normalization** — `resume_renderer.py` normalizes smart typography (curly quotes, em dashes, ellipses, zero-width chars) to plain ASCII before PDF rendering so ATS parsers can read keywords
- **Keyword extraction** — Resume optimizer extracts 10-15 JD keywords in a first pass, then weaves them into the resume. Response format: `{"keywords": [...], "resume": {...}}`
- **Job fit scoring** — After dedup, `score_jobs_fit()` uses a batched LLM call to rate each job 1-5 against the candidate's resume. Scores/rationales stored in `jobs.json` and propagated to `applications.json`
- **Optimization caching** — `save_tailored_resume()` stores a sha256 hash of (resume + JD). `find_cached_resume()` checks hash before calling the API, skipping redundant optimization calls
- **Batch project selection** — `batch_select_projects()` selects projects for multiple jobs in one LLM call. Used in pipeline and apply loops; `select_projects()` still used for single-job optimize command
- **Dry run mode** — `apply --dry-run` fills forms and takes screenshots but never submits or logs to applications.json
- **ATS detection** — companies.json stores detected ATS per company. Never re-detect on apply — trust what's in companies.json
- **Persistent browser state** — `_apply_worker` and `_batch_apply_worker` thread `profiles/{name}/browser_state.json` into Playwright via `storage_state`, save it back in the `finally` block. Cookies + localStorage carry across runs, so previously-completed 2FA does not re-prompt
- **Application status lifecycle** — `applications.json` entries carry `status` (extended enum: applied, screen, technical, onsite, offer, rejected, failed, review_pending, skipped), `status_updated_at` (re-stamped on every change), `source` (`autoapply` | `manual` | `email`), and optional `email_thread_ids` (Gmail thread ids that informed the entry, used by the inbox matcher for thread-id pinning on subsequent emails)
- **UI module** — `src/ui/` is the FastAPI dashboard, the project's only user surface. It reads `Profile`, calls `_save_applications`, `discover_jobs`, `_save_companies`, `validate_profile`, `validate_responses`, `expand_roles`, and `validate_slug` — no rewrites of business logic. Routes live under `src/ui/routes/`. State lives in `src/ui/state.py` (active profile env-var + per-profile `threading.Lock` registry; mutating routes acquire the lock, apply uses non-blocking acquire and returns 409 if held — kept available for future direct-apply use). Templates use HTMX for partial swaps and Sortable.js for kanban drag-and-drop. Design tokens (dark theme — deep canvas `#0d0e13`, raised `#16171d`, sunken `#07080b`, elevated `#1c1d24`; Geist Sans + Geist Mono; indigo accent `#818cf8` with violet-shifted wordmark gradient; smooth motion via cubic-bezier easing) live in `src/ui/templates/base.html`. Three-tier button hierarchy: `btn-primary` (indigo gradient + glow on hover), `btn-secondary` (indigo-tinted, less heavy), `btn-ghost` (dark elevated surface). `.btn-sm` modifier for compact inline actions
- **Inbox integration** — `src/inbox/` is a read-only IMAP scraper running as a background daemon thread per profile, streaming proposals to disk as it works. Pipeline: `fetch.list_message_headers_since` (cheap header-only bulk FETCH, ~500 UIDs/round-trip) → `sync._prefilter` (drops LinkedIn/Indeed/etc.) → `fetch.populate_bodies` (full RFC822 bulk FETCH on prefilter survivors only, ~50 UIDs/round-trip, with reconnect-on-failure retry) → `_classify_chunk` dispatches to `classify.classify_messages` (Haiku 4.5, batched, parallelism=2, sliding-window token-bucket throttle) OR `keyword_classify.classify_messages` (regex-only, no API calls — "free mode" for users without credits). Each chunk's classifier output flows to `matcher.match_application` which consults multiple signals in order: stored `email_thread_ids`, classifier-extracted company, sender domain stem (skipping ATS relays), subject prefix `Company - …`, and body scan against existing application company names. Proposals stream into `profiles/{name}/imap/proposals.json` per chunk; `state.json` tracks `last_sync_at` and `processed_message_ids` (capped at 10K) so re-syncs skip already-seen messages; `sync_status.json` carries live progress for UI polling. Three dedup guards: (a) message-id dedup at fetch time, (b) `new_application + match` proposals silently skipped (re-confirmations don't create duplicate entries), (c) `status_update` proposals that would be no-ops skipped. One fallback: `status_update + no_match` upgrades to `new_application` with the proposed status, so an orphan interview invite for an externally-applied job surfaces as "create new entry at screen" rather than getting dropped. Proposals are reviewed manually — **never auto-apply silently.** Apply mutates `applications.json` via `_save_applications` (schema validation runs), tagging entries with `source="email"` and appending the thread id to `email_thread_ids`. Credentials at `profiles/{name}/imap/credentials.json` as `{email, password, server, port}`
- **Background tasks** — `src/tasks/runner.py` is the shared task runner. `start_task(task_key, status_file, target, args, initial_status, ...)` writes initial `state="running"` synchronously, spawns a daemon thread keyed by `task_key` (`f"{kind}:{profile}"`), and `run_with_terminal_status` traps exceptions and normalizes terminal states (`idle` / `cancelled` / `error`). Status file writes are atomic (tmp + rename). `read_status` sanity-checks `state="running"` against the registered thread; mismatch surfaces as `interrupted` so a uvicorn restart doesn't leave a zombie "running" badge. Cancel is cooperative via `request_cancel` (flips a flag in the status file) + `is_cancel_requested` (polled by workers at chunk boundaries). Inbox sync (`inbox.sync.start_background_sync`) was the original consumer and is now a thin wrapper around the runner; future task kinds (discover, optimize, apply, pipeline) reuse the same machinery. UI polls `/email/sync_status` every 4s — the polling element renders without an `hx-trigger` when status is idle, so polling stops naturally
- **Rate limiting** — `src.api.reserve_input_tokens(n)` is a sliding-window token bucket shared across threads. Calls block until the past-60s window has room for `n` more tokens. Default budget 45K input TPM (override with `AUTOAPPLY_INPUT_TPM_BUDGET`). Used by `classify_batch` to throttle the classifier under Anthropic Tier 1 limits without 429-and-retry-storm
- **Claude response parsing** — `src.api.strip_code_fences(text)` is the single helper for stripping optional ` ``` ` / ` ```json ` / ` ```python ` markdown fences from Claude responses before `json.loads`. Used by every module that calls `create_message` and expects JSON back (`resume_optimizer`, `resume_parser`, `role_expander`, `jobs/classify`, `cold_email`, `inbox/classify`). Handles no-trailing-fence and no-newline-after-opening-fence cases the inline pattern silently crashed on
- **Cold outreach package** — `src/outreach/` is the feature directory: `generator.py` (single + batched Claude drafts with hard-fallback skeletons so a bad response never blanks the editor), `sender.py` (SMTP via the **same app password** stored in `profiles/{name}/imap/credentials.json` — SMTP host derived from IMAP host `imap.gmail.com` → `smtp.gmail.com`, port 587 STARTTLS, `certifi`-backed SSL so the python.org macOS distribution can verify Gmail's cert), `store.py` (`outreach.json` load/save + STATUSES enum), `csv_import.py` (bulk paste → row dicts), `gmail.py` (compose URL + domain normalization for the email-pattern suggester). UI route `src/ui/routes/cold_email.py` is a thin handler that imports from `src.outreach` — CRUD + bulk-import CSV + generate-all-empty + status transitions + send + delete. The send button is the primary action; the Gmail compose URL is kept as a small secondary fallback for attachments / sending from a different account
- **Resume package** — `src/resume/` groups the four resume-processing modules: `parser.py` (PDF → structured resume.json via Claude), `optimizer.py` (tailor against JD + caching via sha256 hash), `renderer.py` (HTML/CSS → PDF via WeasyPrint), `diff.py` (per-section before/after for the optimize page). External callers import from the submodules directly (`from src.resume.optimizer import optimize_resume`)
- **Shared route helpers** — `src/ui/pipeline.py` carries the shared kanban taxonomy AND the data-loading helpers (`load_applications`, `load_jobs`) that route files import. Each route still exposes a thin `_load_jobs = load_jobs` alias for local readability; the single implementation lives in pipeline.py

## Key Rules
- `profiles/` is gitignored — never commit personal data
- Greenhouse, Lever, and Ashby supported today — no Workday, no Crunchbase
- Apply runs from `/jobs/{idx}/apply` (single) or `/apply/batch` (multi-job) via `src/ui/routes/apply.py` → `_apply_worker` / `_batch_apply_worker` → `src/applicant._process_job`. Both modes share the task key `apply:{profile}` and the `apply_status.json` file so only one Playwright session runs per profile. The status file's `mode` field (`"single"` or `"batch"`) drives view selection. Batch's `_partition_selected` runs composite-key dedup against `applications.json` up front (recorded as `skipped_duplicate` in `completed_results`) so the browser never opens for an all-dupes batch. Submit "quit" returns True from `_process_job` to break the batch loop; remaining selected indices get marked `not_attempted`. Every decision boundary (Submit y/n, CAPTCHA pause, email verification) goes through `src/tasks/prompt.py` so the worker blocks on the dashboard modal — never on stdin. `_process_job` requires `captcha_handler` and `submit_handler` kwargs (optional `verification_handler(email)`); there is no terminal fallback
- **Apply stage helpers** — `_process_job` is a thin orchestrator (~85 lines) that composes 5 single-purpose stages: `_prepare_tailored_resume` (find cached PDF or generate via Claude), `_fill_with_captcha_retry` (ATS dispatch + one CAPTCHA-pause retry), `_record_failure_entry` (save progress + log failed entry), `_decide_submit_action` (dry-run / auto / prompt + handles `_handle_post_submit_verification`), `_record_success_entry` (write applied/skipped/review_pending entry). Each stage is 27-71 lines, takes its own args explicitly (no shared mutable context object), and is unit-testable by mocking its inputs
- Everything user-facing must be configurable through the dashboard — users should never need to manually edit JSON files
- All commands that need file paths (import-resume, add-projects) prompt interactively if --pdf is omitted
- Resume stored as structured JSON, rendered to PDF — never edit PDFs directly
- Deduplication by composite key (company + role + posting URL)
- Rate limit Playwright submissions — respect `rate_limit_seconds`
- The dashboard is bound to 127.0.0.1 with no auth — single-user, single-machine assumption. Do not add network exposure or auth without an explicit ask
- **Inbox reads are strictly read-only** — `imaplib` only ever calls `select(readonly=True)` and never `STORE` / `EXPUNGE`. Inbox sync does not mutate the user's mailbox
- **Outbound SMTP is for cold outreach only** — `src/email_send.py` writes to the mailbox (sends mail from the user's account) via the same app password as IMAP. Triggered by an explicit user click on **Send email** with a confirm dialog naming both recipient and sender. Do NOT add silent / automatic send paths; the confirmation gate is the only sanctioned way mail leaves the system
- Email-driven application changes always go through the review queue. Do not add silent auto-apply paths without an explicit ask, even for high-confidence matches
