# Lessons Learned

1. **Custom question answers must be concise** — Answer like a human would on a form. "June 2026" not "I would be available to start immediately after my graduation in June 2026. Given my recent experience...". No essays, no filler, no "excited about the opportunity" language. 1-2 sentences max for open-ended, bare values for factual questions.

2. **Read description divs for real question text** — Greenhouse forms use a pattern where the label is a section header (e.g. "(Optional) Personal Preferences") and the actual question (e.g. "How do you pronounce your name?") is in a `div.question-description` referenced by `aria-describedby`. Always check `#{q_id}-description` for the real question before falling back to the label.

3. **`apply` must be self-contained** — The `apply` command should auto-generate a tailored resume if one doesn't already exist for the job, rather than requiring `optimize` to be run separately. Every command should work standalone without requiring the user to remember prerequisite steps.

4. **Never fill a field with non-answers** — If the model can't answer or there's no real question, leave the field blank. Filling fields with "I don't see a question" or explanations is a dead giveaway for automated applications. Use a SKIP sentinel so the model can signal "don't fill this" cleanly.

5. **Smart optional question handling** — Don't blanket-skip all optional questions. Three tiers: (a) always skip purely personal/subjective ones (pronounce name, preferences, pronouns), (b) skip data-dependent ones only if user lacks the data (website, portfolio, referral), (c) still answer job-relevant optional ones (start date, timelines). Don't assume a field is useless — website/portfolio/referral strengthen applications when the user has them.

6. **Reference designs are inspiration, not templates** — When the user shows a design from another project as a reference for "the kind of look I want", treat it as a vibe to ground around (clean, frosted, editorial, etc.) rather than a recipe to clone token-for-token. The plan-text instruction to copy verbatim came from me, not from the user; the user wanted a clean original look. Default to deriving an original direction with the user's chosen aesthetic, and confirm before implementing if the framing is unclear.

7. **User data files are not test fixtures** — `profiles/{name}/applications.json` (and `companies.json`, `responses.json`, `profile.json`) hold real user data, not test scaffolding. Tests that POST/PATCH/DELETE through routes mutate that data. **The protection is the `_test_*` profile pattern**, not the test-file location: every test uses a unique profile name like `_test_apply` or `_test_batch_apply`, and tears down with `shutil.rmtree` so it can never touch real user data. Phase 37 moved tests from `/tmp` into the repo's `tests/` directory (pytest-discoverable for portfolio/CI) — the convention works equally well in either location, what matters is that no test ever assumes a real profile or mutates one.

8. **Email-driven application changes always go through the review queue** — Every inbox-proposed status change must require an explicit user click on a proposal card; never silent auto-apply, even on high-confidence matches. **Why:** classifier errors compound; a silent path propagates them invisibly. **How to apply:** any mutation to `applications.json` triggered by inbox sync must originate from a user-initiated request (e.g. `/email/proposals/.../apply`). The same review-queue caution does NOT apply to Playwright apply itself — post-Phase 23+, apply runs from the UI but blocks on the user at every decision boundary via `src/tasks/prompt.py`.

9. **Cross-route imports between sibling route modules are a smell** — When `src/ui/routes/email.py` imports from `src/ui/routes/applications.py`, that's pointing at code organization that wants to move up: shared taxonomy belongs in a `src/ui/pipeline.py`-style sibling, not a route-private module. Catch this before commits accumulate; it's painless to extract a constants module early and painful to untangle a circular-import-ready graph late.

10. **LLM rate limits are structural — token bucket beats retry-and-backoff alone** — When multiple worker threads share a Tier-1 TPM ceiling, blind exponential-backoff retries thunder-herd into the same window and 429 again. A sliding-window token bucket with conservative chars→tokens estimation lets bursts run at full speed up to the cap and waits exactly long enough for old usage to roll out. **Why:** simpler than implementing Retry-After parsing, works without changes to the SDK, and degrades to no-op when the budget is generous. **How to apply:** any time multiple concurrent callers share a per-minute API quota.

11. **Background workers + streaming UI polling beat long blocking HTTP requests** — A 5-minute deep sync as a synchronous POST means the user stares at a browser spinner and may time out client-side. A daemon thread + status-file + 4s poll loop means the response returns in 50ms with an in-progress banner, proposals stream in as they're produced, and the user can cancel mid-flight. **Why:** browser timeouts, no progress feedback, and "did it work?" anxiety. **How to apply:** any synchronous handler whose 95th-percentile runtime exceeds 30 seconds.

12. **Reference-design feedback is often "I don't like the *vibe*", not literal copy-this** — When the user said "make it more Vercel" they didn't want pure black-and-white Vercel.com pixels; they wanted "feel like a modern product that ships." Two design pivots later (editorial → vercel-clean → modern with motion → dark theme) we got there. **Why:** vibe is high-bandwidth and low-fidelity; users describe the destination, not the recipe. **How to apply:** when a user pushes back on aesthetic direction, propose concrete options with previews via AskUserQuestion rather than re-guessing.

13. **Match emails to existing apps through multiple independent signals, not just thread_id** — Companies often use multiple email systems (Bloomberg confirmations from `bloomberg.avature.net`, rejections from `bloomberg.com`) so RFC 822 thread chains don't link follow-ups to original confirmations. Match by: thread_id → classifier company → sender domain stem (skipping ATS relays) → subject prefix → body scan against known applications. **Why:** any single signal has 5-20% false-negative rate; the union has <1%. **How to apply:** to any system that tries to thread inbound messages back to known entities — same pattern applies to support ticket dedup, CRM lead matching, etc.

14. **Dedup at the proposal generation layer, not just message-id layer** — Skipping already-seen messages by Message-ID prevents re-classifying, but doesn't prevent a *fresh* re-confirmation email (different message id, same kanban entry) from creating a duplicate. Add a dedup guard at the proposal-building step: if `action_type=new_application` and matcher returns `match/ambiguous` (company already on board), skip. **Why:** the first layer dedupes work; the second dedupes intent. **How to apply:** any pipeline that takes raw events and produces user-actionable proposals against an existing state.

15. **Stale uvicorn vs reloaded templates produces "ghost" bugs** — Without `--reload`, uvicorn keeps Python modules loaded across edits, but FastAPI's Jinja2Templates re-reads HTML from disk per request. So a partial-reload state is normal during dev: template references variables the route doesn't pass yet, or POSTs to routes that don't exist yet — both look like real bugs but actually clear after a process restart. We hit this twice in one session: a "Fit scores not available" banner that fired when `fit_scored` was Undefined; a `POST /cold-email` returning 405 because the route was added without restarting uvicorn. **Why:** mixed-reload state is a real failure mode that masquerades as logic bugs and burns minutes. **How to apply:** (a) in dev, default to running with `AUTOAPPLY_DEV=1` so uvicorn auto-reloads on file changes (the launcher reads this env var); (b) write templates defensively against `Undefined` (e.g. `{% if x is defined and x == false %}` not `{% if not x %}`) so a partial-reload state degrades to "nothing rendered" rather than "wrong thing rendered"; (c) when a user reports a UI bug right after a refactor, first response is always "did you restart uvicorn?"

16. **Documentation drifts silently during long-build sessions — update it as you go, not at the end** — In a 30-phase session we added cold outreach, SMTP send, the `strip_code_fences` helper, and a `load_jobs` consolidation, but CLAUDE.md / README.md / tasks/todo.md were only fully updated at the very end (after a doc audit). Worse: a key rule said "never SMTP" while we'd just shipped SMTP, which is the exact kind of stale-rule a future session would over-index on. **Why:** docs at the end of a session are an afterthought; docs at the end of each phase are a checklist item. **How to apply:** treat the doc update as part of the phase's "definition of done" — todo.md gets the phase entry written *as* the phase ships, and any rule in CLAUDE.md that the phase contradicts gets updated in the same diff. Run a "do the docs match the code?" grep before declaring a phase shipped.

17. **UI surface changes need browser verification before commit — pytest is necessary but not sufficient** — Phase 39 (Ashby ATS) shipped with two bugs pytest missed and a browser would have caught in 30 seconds: the companies schema enum didn't include `"ashby"` (every Add-company POST 500'd), and the route returned a partial template instead of a 303 redirect (form submit rendered an unstyled naked page). Unit tests with pre-validated fixtures don't exercise the integration paths users actually hit. **Why:** "tests pass" proves structural correctness (routes register, templates render, no Python errors). It does NOT prove feature correctness (does the dropdown show the new option, does the form post cleanly, are the styles integrated, do click handlers fire). **How to apply:** for backend-only changes (data layer, helpers, tests), pytest-pass-then-commit is fine. For UI surface changes (route handlers touched, templates touched, dropdowns/forms/buttons modified), either (a) start uvicorn + click through the surface before committing, or (b) explicitly tell the user "this isn't browser-verified, OK to commit anyway or should I verify first?" and wait for permission. The explicit-flag-and-ask path is acceptable; silently committing UI changes is not.

18. **Don't recompute paths inline with `Path(__file__).parent.parent` — use a single source of truth** — Phase 34 moved `src/resume_parser.py` → `src/resume/parser.py` (one level deeper into a package). The path computation `Path(__file__).resolve().parent.parent / "config"` silently broke because `parent.parent` now resolved to `src/` instead of the repo root. Same regression hit `src/resume/renderer.py`. Two other files happened to still work (they're at `src/` top level) but were one careless future move away from the same bug. **Why:** inline path arithmetic encodes a specific filesystem depth into every callsite. The moment a file moves, the path breaks — and the break is silent until something actually tries to read the file at runtime. **How to apply:** define repo-relative path constants ONCE in `src/paths.py` (`REPO_ROOT`, `CONFIG_DIR`, `PROFILES_DIR`). Every other module imports from there. Never write `Path(__file__).parent.parent...` outside `src/paths.py` itself. A move-the-file refactor then has zero path-resolution side effects.
